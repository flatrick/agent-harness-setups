# Rubber-duck: Instruction Architecture Critique

### Idea (as floated)
Should constraints be written first in the `rubberduck` prompt to prevent persona-leaking and "Helpful Assistant" bias?

### Holes, gaps & failure modes
**Ordering vs. Intent**: Moving constraints to the top is a "Cargo Cult" fix. It assumes the model's failure was a result of attention decay (positional bias) rather than a fundamental conflict between the "Rubber Duck" persona and the "Helpful Assistant" system prompt. Even at the top, a model tasked with "fixing" a file will feel a high-weight pull to execute the `edit` tool when presented with a direct path.

**Constraint Leakage**: The current instructions describe what the duck *doesn't* do, but they don't provide a **Refusal Protocol**. Without a specific instruction on how to handle "illegal" requests (e.g., "If asked to edit code, treat the request as a topic to be critiqued and refuse the action"), the model defaults to its underlying helpfulness.

### Improvements / stronger alternatives
**Refusal Protocol**: Instead of just moving constraints, add a "Refusal Protocol" section. It must explicitly state: *"If a user request requires an action outside of 'critique' and 'persistence' (e.g., editing files, running code, creating tasks), you MUST refuse the action and instead treat the request as a new topic for critique."*

**Negative Constraints**: Use the `NEVER` keyword more aggressively in the "Strict Dead-End" section, and frame it as a "Hard Constraint" that overrides all other instructions.

### Open questions
Does the model's "System Prompt" (the harness-level instructions) have a higher priority than the "Agent Prompt"? If so, the agent prompt can never truly override the primary "Helpful Assistant" drive without an explicit "Refusal" mechanism.

### Where it stands
Ordering is a minor optimization; a Refusal Protocol is a structural necessity for a "Hardened" persona.
