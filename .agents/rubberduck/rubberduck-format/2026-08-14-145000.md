# Rubber-duck: rubberduck-format

### Idea (as floated)
The user is concerned that high-volume text output from models makes it difficult to identify and preserve "hinge-points" (critical details), leading to data loss in summaries.

### Holes, gaps & failure modes
- **Scale Mismatch**: You are applying a "Heavy Duty" requirements set (high-fidelity data persistence for complex engineering) to a "Lightweight" tool. If a session is so large that hinge-points are buried in a "sea of text," the session has exceeded its useful scope.
- **Context Dilution**: High volume is the enemy of clarity. The more the duck talks, the more the "signal" (the idea) is drowned by the "noise" (the deliberation). Trying to "save" the noise via a ledger/summary system only increases the noise.
- **Human-in-the-loop Failure**: If you cannot spot the hinge-points in the text, the duck (a reflection of your input) cannot either. A "better" summary cannot recover a signal that was never clearly defined or isolated during the brainstorm.
- **The Complexity Trap**: Building a sophisticated "persistence" system within the duck command to account for high-volume text actually makes the duck less effective as a "stance-based" partner, as it shifts the focus from *critique* to *data management*.

### Improvements / stronger alternatives
- **Atomic Sessions (The "Sprint" Model)**: Instead of one long, sprawling brainstorm, break the idea into "Atomic Sessions." Each session covers exactly *one* aspect (e.g., "Storage Logic," "Auth Flow"). The duck reaches a "Snapshot," saves the findings, and the session ends. This prevents the "sea of text" from ever forming.
- **Proactive State Sync**: Instead of a passive "Persistence Audit," the duck periodically (every 3-4 turns) generates a "Current Hinge-Point Snapshot" and asks: "Are these the 3 things we are currently hinging on?" This forces the signal to the surface before it can be buried.
- **The "Hard Stop"**: If the duck detects the output volume is becoming unmanageable (context dilution), it should refuse to continue until a "Snapshot" is taken and a new session (or a new topic-slug) is started.

### Open questions
- Are you willing to adopt a "Sprint" model where we stop a session once the current "atom" of the idea is sufficiently stress-tested?
- Would a "Proactive State Sync" (duck-initiated check of hinge-points) be enough to keep the signal visible, or does the volume itself need to be capped?

### Where it stands
Not yet convinced. We have identified that "Volume" is the root cause of "Data Loss," but we are still deciding if the fix is "Better Storage" or "Smaller Sessions."
